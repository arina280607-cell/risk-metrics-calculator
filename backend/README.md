# Backend: расчёт DV01

Backend использует PostgreSQL по схеме `../bd.mmd`.
Инструкция по устройству и запуску БД — [DATABASE.md](DATABASE.md).

## Первый запуск

Из корня проекта:

```sh
docker compose up -d --wait db
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
cd backend
python -m app.init_demo_db
python -m app.check_demo_db
python -m uvicorn app.main:app --reload
```

В Windows для активации окружения использовать `.venv\Scripts\Activate.ps1`.
Документация API после запуска: http://localhost:8000/docs.

Настройки подключения читаются из переменных окружения или файла `.env`
в корне проекта. Пример — корневой `.env.example`.
При занятом порте 5432 указать в `.env` `POSTGRES_PORT=5433`;
Docker и backend используют это значение.
`POSTGRES_HOST` по умолчанию равен `localhost`.

## Учебные данные

`python -m app.init_demo_db` добавляет набор за **27.10.2026**:
7 инструментов, 6 записей параметров и курсы RUB = 1, USD = 90.
Все значения и идентификаторы учебные и предназначены для проверки расчёта.
Это не загрузка из Cbonds и не рыночные котировки.

Параметры успешных примеров:

| ISIN | Валюта | Номинал | Цена с НКД, % | Модифицированная дюрация, лет | Выпуклость | Купон | Выплат в год |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `RU000A000008` | RUB | 1000 | 86.5798 | 3.5255 | 16.2622 | fixed | 2 |
| `RU000A000016` | RUB | 1000 | 100.3000 | — | — | floating | 4 |
| `RU000A000032` | USD | 1000 | 94.7579 | 2.6760 | 8.7779 | fixed | 2 |
| `RU000A000040` | RUB | 1000 | 101.7833 | 0.8880 | 1.2158 | fixed | 2 |

Цена, дюрация и выпуклость фиксированных облигаций рассчитаны по согласованным
учебным денежным потокам с двумя выплатами в год. Для рублёвого выпуска
приняты купон 12%, доходность 16% и остаточный срок 5 лет; для долларового —
6%, 8% и 3 года; для короткого рублёвого — 18%, 16% и 1 год.
Оценка сделана на купонную дату с нулевым НКД, значения округлены до 4 знаков.
Эти допущения описывают примеры и не требуют новых полей БД.
Курс USD = 90 также задан для теста, а не взят за указанную дату из источника.
Для плавающего купона калькулятор использует приближение: дюрация 1/4 года,
выпуклость 0.

Повторный запуск не дублирует набор и не изменяет существующий набор за ту же дату.
Все записи и публикация создаются в одной транзакции: при ошибке загрузка отменяется.
Пустые дюрация или частота купона в отдельных примерах оставлены намеренно,
чтобы проверить ошибки при расчёте.

В чистой учебной БД для количества **100** ожидаются такие результаты в рублях
(в таблице DV01 округлена до 6 знаков; API возвращает полную точность):

| ISIN | Назначение | Стоимость позиции | DV01 / ошибка |
| --- | --- | --- | --- |
| `RU000A000008` | Фиксированный купон, RUB | 86579.8 | -30.516669 |
| `RU000A000016` | Плавающий купон, 4 выплаты в год | 100300 | -2.507500 |
| `RU000A000032` | Валютная позиция, USD, курс 90 | 8528211 | -2281.774965 |
| `RU000A000040` | Короткая рублёвая облигация | 101783.3 | -9.037738 |
| `RU000A000024` | Инструмент есть, параметров нет | — | `PARAMETER_SNAPSHOT_NOT_FOUND` |
| `RU000A000057` | Нет дюрации для фиксированного купона | — | `MISSING_INSTRUMENT_PARAMETERS` |
| `RU000A000065` | Нет частоты выплат для плавающего купона | — | `MISSING_INSTRUMENT_PARAMETERS` |
| `RU000A000073` | Корректный ISIN, которого нет в справочнике | — | `INSTRUMENT_NOT_FOUND` |

Последний ISIN намеренно не добавляется в БД.
Для короткой позиции можно передать количество `-100`:
знак стоимости позиции и результата изменится.

Пример запроса к `POST /api/v1/calculations/dv01`:

```json
{
  "trades": [
    {"isin": "RU000A000008", "quantity": 100},
    {"isin": "RU000A000032", "quantity": 100}
  ]
}
```

Ожидаемый итог — `-2312.2916332831977` RUB.
Ошибки отдельных сделок не мешают расчёту остальных.

## Как выбираются данные

Используется последний по торговой дате набор со статусом `PUBLISHED`.
Более новый набор со статусом `LOADING` не участвует в расчёте.
Параметры и курс соединяются по двум полям: `snapshot_id` и `currency`.
Все сделки одного запроса читаются в одной согласованной транзакции.

В ответе `snapshot` содержит `id`, `as_of_date` и `published_at`.
Старые поля `version` и `source` из SQLite больше не возвращаются:
в согласованной схеме этих полей нет. Фронтенд расчёта их не использует.
Отдельное хранение источника нужно согласовать перед подключением реального API.

Если в БД есть более поздний опубликованный набор, API выберет его,
поэтому учебные значения из таблицы могут не использоваться.

## Проверки

При запущенной БД, из каталога `backend` с активным окружением:

```sh
python -m pytest -q
```

Тесты используют отдельные временные схемы PostgreSQL и удаляют их после проверки.
Рабочие таблицы и загруженные в них данные не изменяются.
Проверяются расчёты, валютный курс выбранного набора, ошибки данных,
повторное заполнение и отмена неудачной загрузки.

Ошибка недоступности внешнего API здесь не имитируется:
подключение источника реализуется отдельной задачей.
